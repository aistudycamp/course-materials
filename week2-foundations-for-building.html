Learn by shipping

The goal is not to memorize commands. The goal is to understand the system well enough to direct Claude and catch problems.

This week's app

You will build a small to-do app. A user can see a list of tasks, add a task, change it, mark it complete, and remove it. The app should remember the tasks after a browser refresh. Later, you can add accounts so each user sees their own tasks.

User

A person who wants to keep track of tasks.

First version

View, add, edit, complete, and delete tasks.

Data

Task text, completion status, and timestamps saved in Supabase.

Later

Accounts, sharing, reminders, and other features can wait.

Why plan first?

Claude can write code whenever you ask. If the idea is unclear, that speed creates the wrong screens and the wrong data model very quickly. A plan gives Claude a target. It also gives you something concrete to review before the project grows.

What is a PRD?

A PRD is a Product Requirements Document. It is a short description of the user, problem, main flow, first features, data, visual direction, and out of scope work. It is not a technical specification. It is the product decision that the technical work follows.

What is Plan mode?

Plan mode is a pause before building. Claude reads the project context, asks questions, points out weak decisions, and proposes a sequence of work. It should not edit the app until you approve the PRD and the build plan.

PRD

The product decision you will review.

Plan mode

The conversation where Claude asks and challenges.

Build plan

The ordered steps Claude proposes.

Approval

Your signal that the plan matches your intent.

Use Plan mode

Open Claude Code inside week-2-todo-app. Choose Plan mode. Give Claude the problem you want to solve. Ask it to ask one question at a time and to keep going until the user, flow, data, and first version are clear.

  • Make a plan large enough to cover the user flow, pages, data, and risks.
  • Ask Claude to grill you on unclear or unnecessary features.
  • Read the PRD and build plan yourself.
  • Change anything that does not match what you want.
  • Approve only after the product and the order of work are clear.
Tell Claude: I want to build a small to-do app. Stay in Plan mode. Ask me one question at a time about the user, the problem, the main flow, the visual direction, the data we need to save, and what should wait. Challenge weak or unclear parts of my idea. Save the PRD as PRD.md and the build plan as PLAN.md in this project folder. Do not write code until I approve both files.

PRD template

Use this template, or choose another format that fits your preference and the scope of the project.

# Product Requirements Document ## User Who is this for? ## Problem What problem does it solve? ## Main flow What does the user do from opening the app to getting value? ## Core features 1. 2. 3. ## Data What needs to be saved after a refresh? ## Visual direction What should it feel and look like? ## Out of scope What will wait until a later version?

What makes an app work?

A full-stack app has several parts. They use different kinds of code, but they work together as one product.

Frontend

The screens and controls in the browser. Common building blocks include HTML for structure, CSS for appearance, and JavaScript or TypeScript for behavior. React and Next.js are tools built with JavaScript or TypeScript.

Backend

The code behind the screen. It handles rules, requests, authentication, and work that should not run in the browser. Common backend languages include JavaScript or TypeScript, Python, Ruby, and Go.

Database

An organized place to store records. This app stores tasks and accounts in Supabase, so the data remains after a refresh and can be used by more than one device.

Hosting

A service that runs the app on the internet. Vercel builds and serves the project at a public URL. Supabase hosts the database separately.

Why use a database?

A screen can hold a task for a moment, but browser memory can disappear when the page refreshes. A database gives the app a lasting place to save information. It also lets the backend apply rules, lets accounts own their data, and lets the same app work across devices.

Keep the locations straight:
The code is local in week-2-todo-app. The database is a hosted Supabase project in your account. Vercel will host the app later. No Supabase installation goes inside the local folder.

Build

Now give Claude the approved plan and build the app in small, visible slices. Each slice ends with a browser check and a clear decision about what to do next.

Start from your PRD

Do not make Claude guess what to build. Your PRD.md explains the product. Your PLAN.md explains the order. In the same Claude Code session, ask Claude to read both files, restate the next slice, and wait for your approval before it changes code.

Tell Claude: Read PRD.md and PLAN.md before you change anything. Restate the product in your own words. Tell me the next smallest slice of work, the files you expect to change, and how I will check it in the browser. Wait for my approval, then build only that slice. Run the app and tell me what to check.

Build in five slices

  1. Core screen: Create the first page and show the empty task list. Check the layout in the browser.
  2. Create and read: Add a task and show the saved task in the list. Refresh and check that it remains.
  3. Change and complete: Edit a task and mark it complete. Check both the screen and the saved data.
  4. Remove and polish: Delete a task, then adjust the layout, labels, colors, and empty states.
  5. Accounts and review: Add sign up, sign in, and sign out only after the core task flow works. Test what each account can see.
Accounts come after the basic flow:
Build the task flow first so you can learn how data moves without debugging account state at the same time.

Keep saying: Make one change. Run the app. Show me how I can check it in the browser. If it does not work, explain the cause before fixing it. Do not start the next slice until I confirm this one works.

What to check after every slice

  • The intended screen appears.
  • The main action works.
  • The data is saved after refresh.
  • Errors are visible and explained.
  • The change matches the PRD.
  • Claude tells you which files it changed.

Publish

Course recording · add before launchTest and publish

Target 15 to 20 min. Watch this before sending the app to a live URL.

Before you publish

You need a GitHub account. GitHub is where the online copy of your project will live. If you do not have an account, create one before asking Claude to push the code.

  1. Go to github.com/signup.
  2. Create the account and verify your email address.
  3. Sign in at github.com.
  4. Keep the account open in your browser when Claude asks to connect GitHub.

Git, GitHub, and Vercel

These names describe different places and jobs. The app moves between them.

Git

Version history for a project on your computer. A commit is a named snapshot of the files at one point in time.

GitHub

An online home for a Git repository. It stores a copy of the code and gives other services a place to read it.

Repository

A project folder tracked by Git. It contains the code and its version history.

Vercel

A hosting service. It reads the repository, builds the app, and serves it at a public URL.

The simple picture:
Git saves versions on your computer. Push sends a version to GitHub. Vercel reads GitHub and builds the live app. A later commit and push gives Vercel a new version to build.

Local values and live values

Your local app reads values from .env.local. The live Vercel app needs the same connection values in its project settings. Add NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY in Vercel. Never add the service role key or database password.

Publish in five steps

  1. Check local: Open the local URL. Test sign in, task changes, refresh, and sign out.
  2. Review files: Ask Claude to check for secrets and show the files it plans to commit. Do not approve a service role key, database password, supabase.md, or .env.local.
  3. Commit and push: After you approve the file list, ask Claude to initialize Git if needed, create the repository, commit the working version, and push it to GitHub.
  4. Connect Vercel: Open Vercel, connect GitHub, choose the repository, and add the two public Supabase environment values.
  5. Test live: Open the public URL. Test the same flow again. A live app is not checked until the browser can save and retrieve data.
Tell Claude: Review this project for exposed secrets. Show me the files you would commit and stop for my approval. After I approve, initialize Git if needed, create a GitHub repository for this project, commit the working version, and push it to GitHub. Do not commit supabase.md, .env.local, the service role key, or the database password. Then tell me what I need to add in Vercel before I deploy.

Keep the live URL and a short final test note for your Week 2 submission.

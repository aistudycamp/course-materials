AI for Building · Week 2

Foundations for Building

Move from the desktop app into a development environment. Learn what the parts of a full-stack app do, then build and publish one with Claude Code.

Your route through Week 2:
  • Step 1: Set up the tech stack and write the PRD.
  • Step 2: Create the app schema, hold a sync, and connect Supabase.
  • Step 3: Build the design, core features, and authentication.
  • Step 4: Finalize the design and add the last features.
  • Step 5: Test the app, deploy it, and share the live URL.
By the end of the week, you should be able to:
Explain what the frontend, backend, database, and host do. Produce an approved PRD. Build a local app that saves data in Supabase. Deploy it and verify the same flow at a public URL.

HOW THIS WORKS

What you are learning

Build with an agent

Claude Code can read the project, edit files, run commands, and check the result. You still make the product decisions and review the work.

Understand the stack

The frontend is the screen. The backend handles rules and requests. The database stores information. Vercel puts the app online.

Work in a loop

Learn by shipping

Write the PRD

The PRD is the product blueprint. It describes the user, problem, main flow, first features, data, visual direction, and what can wait. The PRD is not code. It is the decision that guides the code.

Tell Claude: I want to build a small web-based to-do app. Stay in Plan mode. Ask me one question at a time about the user, the problem, the main flow, the visual direction, the data we need to save, and what should wait. Challenge weak or unclear parts of my idea. Save the PRD as PRD.md in this project folder. Do not write code yet.

PRD template

Use this template, or choose another format that fits your preference and the scope of the project.

# Product Requirements Document ## User Who is this for? ## Problem What problem does it solve? ## Main flow What does the user do from opening the app to getting value? ## Core features 1. 2. 3. ## Data What needs to be saved after a refresh? ## Visual direction What should it feel and look like? ## Out of scope What will wait until a later version?

Other PRD options: choose the format that fits your preference and the scope of the project. Browse Lenny's favorite product templates.

What is app scaffolding?

Scaffolding is the starting structure for an app. Next.js creates the first folders and files, gives the project a way to run, and provides a place for pages, components, and server code. You are not building the finished product yet. You are creating the frame that the features will use.

Next.js

A framework for building web apps with pages, routing, frontend code, and server functions.

React

A library for building reusable interface pieces, such as a task row, button, or form.

TypeScript

JavaScript with checks that help Claude and you catch some mistakes before the app runs.

Node.js

Runs the local development tools and server-side JavaScript outside the browser.

Create the app

Open Claude Code inside week-2-todo-app. Ask Claude to create the Next.js foundation from the PRD. Claude may use the create-next-app command. You do not need to type it yourself. Watch which files it creates and ask what each main folder is for.

Tell Claude: Read PRD.md. Create the Next.js foundation for this web-based to-do app inside this project folder. Use TypeScript, ESLint, and Tailwind CSS. Explain the folders you create before you create them. Start the local development server and tell me the localhost URL. Do not add features beyond the foundation yet.
Check the browser.
Open the localhost URL Claude gives you. You should see the first app screen. This confirms that the scaffolding runs on your computer.

Connect Supabase

Supabase is the hosted database and account service. The project lives in your Supabase account. The local app stores only the connection values it needs. The database itself does not live inside week-2-todo-app.

  1. Create one Supabase project. Use your course project name, such as ai-study-camp.
  2. Find the project URL and anon public key. These identify the project for the app.
  3. Keep the database password and service role key private. Save them in your password manager. Do not place them in code.
  4. Connect the Supabase MCP. Ask Claude to guide the browser authorization and confirm the connection.
  5. Store local values in .env.local. Add this file to .gitignore before you save the project online.
Tell Claude: Connect this Next.js app to my ai-study-camp Supabase project. Find or create supabase.md at the AI Study Camp level. Add the project URL and anon public key with notes about what they do. Connect the official Supabase MCP. Keep the service role key, database password, and MCP token out of the project files. Add supabase.md and .env.local to .gitignore. Show me every file you changed and confirm the connection.

Turn the PRD into a build plan

Day 1 gives you the product decision. Day 2 turns that decision into an ordered implementation plan. In Plan mode, Claude asks questions about the design, user flow, database, and risks. It then saves the plan so the conversation does not have to carry every detail.

Tell Claude: Read PRD.md and the project CLAUDE.md. Stay in Plan mode. Ask questions about the user flow, frontend, database tables, authentication, visual direction, and risks. Create PLAN.md with the ordered build steps. Do not edit the app until I approve the plan.
Approve before building.
Read PRD.md and PLAN.md. Change anything that is wrong. Then tell Claude that you approve the plan.

Save the foundation

Start with the approved plan

Give Claude the product context before you ask for code. Ask it to read PRD.md, PLAN.md, and CLAUDE.md. It should restate the next slice, name the files it will change, and tell you how to check the result.

Tell Claude: Read PRD.md, PLAN.md, and CLAUDE.md. Restate the next slice of work. Tell me which files you will change and how I will test the result in the browser. Wait for my approval, then build only that slice.

Build the core task flow

  1. List tasks. Show an empty state and the tasks saved for the signed-in user.
  2. Add a task. Give the user a fast input and save the new record in Supabase.
  3. Change a task. Let the user edit the text and mark it complete.
  4. Remove a task. Add a clear delete action and confirm the record is gone.
  5. Show progress. Add a count of completed and pending tasks if it fits the first version.

Build the design

The design is part of the product. Ask Claude for two or three directions, then choose the one that fits your taste. Decide on layout, type, color, spacing, buttons, empty states, and feedback when a task changes.

Tell Claude: Read the visual direction in PRD.md. Propose three interface directions for the task app. Show the tradeoffs. After I choose one, update the frontend one small change at a time. After each change, start the app and tell me what to inspect in the browser.
Check the browser after every slice.
Do not wait until the end to look at the app. Check the screen, the main action, the saved data, and the empty state each time.

Add authentication

Authentication lets the app know who is signed in. Use Supabase Auth. A user can sign in, see their own tasks, and sign out. The database permissions must stop one user from reading another user's tasks.

Tell Claude: Add Supabase email authentication to the app. Build sign up, sign in, sign out, and a clear signed-in state. Scope task records to the signed-in user. Explain the database policy before you change it. Test that one user cannot see another user's tasks.

Use these Claude Code commands as landmarks

Sessionclaude, /clear, /resume

Start Claude Code, clear the current context, or return to an earlier session.

Inspection/mcp, /model, /config

See connected tools, check the model, or open configuration.

You can ask Claude to run these. The point is to know what each one means.

What is a branch?

A branch is a separate line of work in the same Git repository. The main branch is the version you want to keep stable. A feature branch gives you a safe place to try a design or feature, test it, and review it before you merge it back.

MainStable version
BranchTry a feature
CommitSave a snapshot
PushSend the branch to GitHub
MergeBring tested work into main
Tell Claude: Create a new branch called feature-final-polish. Tell me what branch I am on. Make the design changes from my PRD on this branch only. Commit and push the branch after the local tests pass. Do not merge it into main until I approve it.

Refine the product

  1. Review the core flow. Remove confusing steps and make the main action easy to find.
  2. Add the last planned features. Use PLAN.md as the boundary. Do not add unrelated features.
  3. Add a library when it helps. Motion can add animation. Lucide can add consistent icons. Ask Claude to explain the dependency before adding it.
  4. Run a second review. Ask Claude to inspect the branch for errors, missing states, accessibility issues, and exposed secrets.

What are subagents?

A subagent is a specialist Claude can ask to do a focused piece of work, such as reviewing the UI, checking a database policy, or looking for missing tests. The main Claude session stays responsible for the project. A specialist returns findings or a bounded change for review.

Use a specialist for a clear job.
Ask for one review, give it the files or question it needs, and read the result before you accept changes. Do not add subagents just to add more moving parts.
Tell Claude: Ask a second agent to review this branch for missing tests, broken user flows, accessibility issues, and secrets. Give me its findings in a short list. Do not change files until I approve the findings.

Day 4 is complete when

  • The final design matches the product plan.
  • New features work in the browser.
  • The branch has been tested and pushed.
  • A second review found no blocking issue.
  • You know whether the work is ready to merge into main.

Git, GitHub, and Vercel

Git saves versions on your computer. GitHub stores the online repository. Vercel reads the repository, builds the app, and serves it at a public URL.

Commit

Push

Environment values

Vercel needs the Supabase URL and anon public key in project settings.

Deploy in five steps

  1. Review the files. Ask Claude to find secrets and show the commit list. Do not include .env.local, supabase.md, the service role key, or the database password.
  2. Commit and push. After you approve the files, ask Claude to commit the working version and push it to GitHub.
  3. Connect Vercel. Open Vercel, connect GitHub, and choose the repository.
  4. Add environment values. In Vercel project settings, add NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY. Add them for the deployment environment you use.
  5. Test the live URL. Run the full test again. If deployment fails, show the error to Claude, fix it locally, commit, push, and wait for Vercel to build again.
Tell Claude: Review the project for exposed secrets. Show me the files you would commit and stop for approval. After I approve, commit and push the working version to GitHub. Tell me which public Supabase values I need to add in Vercel. Do not commit .env.local, supabase.md, the service role key, or the database password.

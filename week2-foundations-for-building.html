HOW THIS WORKS

What you are learning

Build with an agent

Claude Code can read the project, edit files, run commands, and check the result. You still make the product decisions and review the work.

Understand the stack

The frontend is the screen. The backend handles rules and requests. The database stores information. Vercel puts the app online.

Work in a loop

Learn by shipping

The goal is not to memorize commands. The goal is to understand the system well enough to direct Claude and catch problems.

STEP 1

Setup

Setup gives Claude a place to work, gives the app a database, and gives you a way to see what is happening.

What you are setting up

VS Code

An IDE, or integrated development environment. It puts the project files, code editor, terminal, and extensions in one workspace.

Claude Code

The coding agent that reads the folder, edits files, runs commands, and reports what it did.

Supabase

A hosted database and user-account service. It stores tasks after the browser refreshes and identifies users.

Supabase MCP

A connection that lets Claude work with the Supabase project without asking you to type database commands.

Open the workspace

  1. Open VS Code.
  2. Choose File → Open Folder.
  3. Select the AI Study Camp folder you created in Week 1.
  4. Choose View → Terminal. The terminal opens at the folder you selected.
  5. Click inside the terminal, type claude, and press Return.

The left side of VS Code shows the files Claude can read and change. The bottom panel shows the terminal where Claude Code runs. The Week 1 desktop app is useful for chat and general work. This week, VS Code plus the terminal is the main interface because Claude needs access to the whole project.

Create the Supabase project

Supabase is not just a file you download. It is a hosted service that gives your app a database, authentication, and a dashboard for inspecting what the app saves.

  1. Go to supabase.com and create a free account.
  2. Click New project and name it ai-study-camp.
  3. Create a database password and save it in your password manager. Do not put this password in the project folder.
  4. Wait for Supabase to finish creating the project.

Connect Claude to Supabase

In the Claude Code session you opened above, paste this prompt. Claude should guide you through the setup and show you what it changed.

Tell Claude: I created a Supabase project called ai-study-camp for my course. Walk me through connecting it safely. 1. Create a file called supabase.md in my AI Study Camp folder. 2. Ask me to copy the Project URL and anon public key from the Supabase dashboard into that file. 3. Never save the service role key or database password in the file. 4. Set up the official Supabase MCP so you can work with this project in future builds. 5. Update the AI Study Camp CLAUDE.md to say that course builds use ai-study-camp, with connection details in supabase.md. 6. Show me the file and confirm that the MCP is connected.
What is supabase.md?
It is a small Markdown note in your local course folder. It names the Supabase project and stores the safe connection details Claude needs. It is not Supabase itself. The actual database lives in the hosted Supabase project.

Setup is complete when

  • VS Code is open on your AI Study Camp folder.
  • Claude Code is running in the VS Code terminal.
  • The Supabase project is named ai-study-camp.
  • supabase.md exists in the AI Study Camp folder.
  • Claude confirms that the Supabase MCP is connected.
  • You know where the project files and terminal are.

STEP 2

Plan

Planning gives Claude a clear product to build instead of a pile of disconnected requests. You will write a short PRD, ask Claude to challenge it, and approve a build plan before code changes begin.

What is a PRD?

PRD means Product Requirements Document. It is the short brief for the app. It explains who uses it, what problem it solves, what the main flow looks like, what data must survive a refresh, and what belongs in the first version.

User

Who is using the app? What are they trying to do?

Problem

What is frustrating, slow, or hard today?

Main flow

What happens from opening the app to getting value?

Version one

What must exist now? What should wait?

Write your brief

Before you ask Claude to build, answer these questions in plain language:

  • Who is this app for?
  • What problem does it solve?
  • What are the three core features?
  • What data needs to survive a refresh?
  • What should the app look and feel like?
  • What will you leave out of version one?

Use Plan mode

Plan mode is a pause before implementation. Claude can ask questions, identify missing decisions, map the pages and data, and show you a sequence of work before it edits files.

  • Use Plan mode before Claude writes code.
  • Make the plan large enough to cover the user flow, pages, data, and risks.
  • Ask Claude to show you the plan before it edits files.
  • Ask Claude to grill you. It should ask questions until the product is clear.
  • Cut the first version down to one main flow and three core features.
Tell Claude: I want to build a small to-do app. Stay in Plan mode. Ask me one question at a time about the user, the problem, the main flow, the visual direction, the data we need to save, and what should wait. Challenge weak or unclear parts of my idea. Then write a PRD and a build plan. Do not write code until I approve the plan.

What good looks like

A good plan tells you what Claude will create, what data the app needs, how the pieces connect, and what you are deliberately leaving out. You should be able to read it and say, “Yes, that is the app I meant.”

Do not skip the questions.
The questions are where you decide what the app is. The build plan is where Claude turns those decisions into pages, data, and small implementation steps.

STEP 3

Foundation

Foundation is where the plan becomes a real project. Claude creates the app structure, connects Supabase, and prepares a local version you can open in a browser.

Before you start:
VS Code is open, Claude Code is running in the project folder, supabase.md exists, the Supabase MCP is connected, and you approved the PRD and build plan.

The parts of the app

Frontend

The screens and controls people see and use in the browser: pages, buttons, forms, lists, and visual design.

Backend

The code behind the screen. It handles requests, rules, authentication, and connections to other services.

Database

A structured place to store information. Your tasks need one because they should still exist after a refresh.

Vercel

The host you will use later. It builds and serves the app at a public URL.

Ask Claude to create the foundation

Tell Claude: Read the PRD and the approved build plan. Create the app foundation with Next.js. Use my Supabase project from supabase.md and the Supabase MCP. Set up the frontend, the database connection, and the first page. Before making changes, explain what you will create and ask me before anything destructive.

How the data moves

BrowserUser clicks
FrontendShows the screen
BackendHandles the request
SupabaseSaves the data

Environment values and secrets

The app needs connection values to talk to Supabase. Local values go in .env.local. Vercel gets its own copy later. These values must stay out of GitHub. The anon public key is designed for the browser when the database rules are set correctly. The service role key and database password are private.

Use one database project, separate the tables.
Keep this build's tables separate from later course builds. Ask Claude to name them with a Week 2 prefix.

Foundation is complete when

  • The project opens in VS Code.
  • The first page opens on localhost.
  • Claude can read the Supabase connection.
  • The app has a frontend and a database connection.
  • No password or service role key is in the code.

When the first page opens on localhost, move to Step 4, Build.

Why accounts come later:
Build the task flow first so you can learn how data moves without also debugging account state. Then connect each task to the signed-in user.
STEP 4

Build

Build one slice at a time. Each slice should end with a browser check, not a wall of new code.

Build in this order

1. Core flow

Add, edit, complete, and delete a task. Refresh and confirm the data is still there.

2. Design

Choose the layout, colors, type, and details. Ask Claude for options, then make the call.

3. Accounts

Add sign up, sign in, and sign out after the basic task flow works.

4. Test

Ask Claude to test the flow, inspect errors, and explain anything unclear.

The loop

AskOne change
RunLocal app
LookBrowser
CheckExpected result
SaveCommit
Keep saying: Make one change. Run the app. Show me how I can check it in the browser. If it does not work, explain the cause before fixing it.

Use the browser as your feedback loop

After every meaningful change, open the local URL Claude gives you. Click through the exact flow a user would follow. Check the frontend, then ask Claude to inspect the data in Supabase when you need to confirm that it was saved correctly.

Do not treat “the code changed” as “the feature works.”
The feature works when the browser shows the right result, the database holds the right data, and the flow still works after a refresh.

When the core flow works locally, move to Step 5, Publish.

Local and live are different:
The local app runs on your computer and uses local values. The Vercel app runs online and needs its own Supabase values. Add NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY in Vercel. A local change reaches the live app only after you commit, push, and let Vercel deploy again.
Keep these artifacts:
Setup gives you the project folder and safe connection note. Plan gives you PRD.md and PLAN.md. Foundation gives you a local app. Publish gives you a live URL and a final test record.
STEP 5

Publish

Publishing moves the app from your computer to a public URL. You will save the code in GitHub, connect the repository to Vercel, add the Supabase values, and test the live app.

Git, GitHub, and Vercel

Git

Git saves versions of your code on your computer. A commit is a named snapshot you can return to.

GitHub

GitHub stores the repository online. It gives you a backup and a place for Vercel to read the code.

Vercel

Vercel builds and serves the app at a public URL. It can redeploy when GitHub receives a new commit.

Environment values

The deployed app needs its own Supabase values in Vercel. They do not come from your local .env.local file.

LocalYour computer
CommitSave a version
PushSend to GitHub
VercelBuild online
LivePublic URL

Publish in five steps

  1. Confirm the app works locally.
  2. Ask Claude to review the files for exposed secrets, then commit and push the working version to GitHub.
  3. Connect the GitHub repository to Vercel.
  4. Add the Supabase environment values in Vercel's settings.
  5. Open the live URL and test sign in, task changes, refresh, and sign out.
Tell Claude: Check the local app one last time. Review the files for exposed secrets. Commit and push the working version to GitHub. Then tell me exactly what I need to add in Vercel before I deploy.

Publish is complete when

  • The code is committed and pushed to GitHub.
  • Vercel has built the repository.
  • The live URL opens in a browser.
  • Supabase values are set in Vercel.
  • Sign in, task changes, refresh, and sign out work live.

You have now built and published a full-stack app with Claude Code.

Your first full-stack app

Your full-stack to-do app

Your to-do app will let someone create an account, add tasks, edit them, mark them complete, and delete them. Their tasks stay saved when they refresh or return later. Each person should only be able to access their own tasks.

By the end of this week, you should be able to:
  • Explain what the frontend, backend, database, authentication, and hosting do.
  • Produce a PRD and an implementation plan you have reviewed and approved.
  • Build a local app with login and tasks that stay saved.
  • Deploy it and test the version real users will open.

Workload estimate: 5 to 7 hours for this exercise, depending on setup and troubleshooting. LMS videos and readings are separate. Stop at the end of a section when you need a break.

How this app works

Full-stack means the visible interface and the services behind it work together. Here is the role of each piece, followed by the tool we use for it.

Frontend

Next.js + React

The browser interface: task list, buttons, forms, and screens.

Hosting

Vercel

Builds and serves your app at a public web address.

↔REQUESTS
RESPONSES

Backend

Supabase API + access rules

Handles requests to read or write task data and checks who is allowed to do so.

Database

Supabase Postgres

Stores users' task records so they do not disappear.

Authentication

Supabase Auth

Identifies the person who signed in.

These are connected responsibilities, not five steps in a line. Supabase supplies the backend services for this app. Next.js can also run server-side code on Vercel if a feature needs it; you do not need to build a separate backend server for this exercise.

When you click Add task, the frontend sends a request with your signed-in identity. Supabase checks the access rules, saves the task in the database, and returns the result for the frontend to display.

Your route through Week 2

Plan before building

Write your PRD

A PRD is a Product Requirements Document. It says who the app is for, what it should do, and how you will know it works. Without one, Claude can produce a working screen that misses the product you meant to build.

For this exercise, build a personal to-do app: a signed-in user can add, view, edit, complete, and delete their own tasks. Start with one task list and a style you like. Leave collaboration, payments, calendars, and notifications out of the first version.

Use Plan mode to think before Claude edits

Plan mode lets Claude inspect and propose an approach without immediately implementing it. In the terminal, use Shift+Tab to cycle modes until the interface says Plan mode. Ask questions and review the proposal before switching back to an editing mode.

You are not trying to write an enormous document. You are trying to make the choices explicit. Ask Claude to interview you one question at a time, point out gaps, and simplify anything that is too much for a first app.

Data and privacy

Give the app a place to save tasks

A database table is a structured list of records. Each row is one task. Each column describes a piece of that task. Unlike a variable in a browser page, a database record remains after you refresh or close the page.

Task fieldWhy it exists
idA unique identifier so the app changes the right task.
titleThe task text the person entered.
completedWhether the task is done.
user_idThe signed-in user who owns this task.
created_atWhen the task was created, useful for ordering the list.

Authentication is not privacy by itself. Signing in identifies a user. Row Level Security (RLS) is the database rule that restricts which rows they can access. Your tasks table needs rules for reading, adding, updating, and deleting your own tasks. Hiding another person's tasks in the interface is not enough.

Tell Claude

Read PRD.md. Propose the simplest Supabase tasks table for this app, including id, title, completed, user_id, and created_at. Prefix this build's tables with sprint1_, such as sprint1_tasks, so future course apps have separate tables. Check existing tables first; do not overwrite another course build's data. Explain the schema and the Row Level Security rules in plain language. Each signed-in user must only read, insert, update, and delete tasks they own. Wait for my approval before applying changes through MCP. Then tell me where to inspect the table and its policies in the dashboard.

Approve after you understand the proposal. Open Table Editor in Supabase and look for the table name Claude used. Confirm the columns, then ask Claude to show where the RLS policies are enabled. The table may be empty now; the interface for adding tasks comes in Step 3.

What the check proves:

The app can reach the intended Supabase project with valid client settings, without a network or invalid-key error. An empty task result is expected before features and test data exist. Access to each user's tasks is tested after login in Step 3.

Keep credentials in the right place.

App settings go in the app's ignored .env.local, not in the PRD or instruction files. A publishable key is intended for client use, but it does not replace RLS. Never “fix” a permission error by disabling RLS or adding a privileged key to the frontend.

Authentication

Add sign-up, sign-in, and sign-out

Now make the app recognize who is using it. Supabase Auth manages accounts and sessions. A session is the signed-in state the app uses to identify you when requesting your tasks.

Check confirmation email delivery before creating accounts

Supabase's default email sender only sends to addresses belonging to the project's team and has a low send limit. It is not a public signup email service. For two test accounts and other people signing up, use the course's configured mail service if one is available, or set up a custom sender with Claude's guidance.

SMTP is the connection to an email provider that sends your app's confirmation messages. This is an authentication setting in the Supabase dashboard, not a new app backend to build.

Choose the issues that affect the promised app first. Ask Claude to fix one issue at a time, then retry the failing behavior. If a proposed fix changes the PRD or adds a feature, decide whether you actually need it.

Evidence, not just “fixed.”

Ask which check Claude ran and whether it passed. Then repeat the browser action yourself. If it involves permissions, verify the database rule as well as the screen.

Everyday use

Polish the parts people touch

  • Empty state: a new user knows how to add the first task.
  • Bad input: a blank task is rejected with a useful message.
  • Waiting and errors: saving has a visible state; failures do not pretend the task was saved.
  • Small screens: inputs and buttons are readable and usable on a phone.
  • Navigation and login: signing out and returning to the app behave predictably.

Change the style if you want to make the app yours, but do not turn polish into a new project. Aim for one coherent design and clear behavior.

When the chosen fixes pass

Run the app's build and available checks again. Review the files for secrets. Commit and push this reviewed version, then summarize any known limitations honestly in README.md. Do not deploy yet.

The app builds, your feature checks still pass after fixes, and the reviewed code is on GitHub. Known limitations are written down. A working course app is not a guarantee of production readiness; broader security, reliability, and eval work comes later.

Step 5 · Publish

Deployment and live testing

Localhost works on your computer. Hosting makes a version available at a public URL. The live version needs its own app settings and login configuration.

Hosting

Deploy your GitHub project on Vercel

GitHub stores the code. Vercel builds and hosts the app. Supabase runs the database and authentication. Deploying does not move your database into GitHub or copy your local environment file to Vercel.

  1. Ask Claude to run the build and confirm the latest reviewed code is pushed to week-2-todo-app.
  2. Open Vercel and create an account or sign in. Choose the plan appropriate for your course/personal project and check any charges before proceeding.
  3. Choose Add New → Project, connect your GitHub account, and authorize access to this app repo. Import week-2-todo-app. Keep the detected Next.js settings unless Claude identifies a reason to change them.
  4. Before deploying, add the Supabase environment variables described below. Their names must match the code.
  5. Deploy. Wait for the deployment to finish, then open the public URL Vercel gives you.

Add the app settings to Vercel

Your ignored .env.local stayed on your computer, as intended. Vercel needs its own copies of the app's project URL and publishable key in the project's Environment Variables settings.

Tell Claude before deployment

Inspect the code and tell me the exact environment variable names this app needs on Vercel, and where to get their values in Supabase. Give me names and purpose without printing secrets. Confirm that the browser client only uses the project URL and publishable key, not a service role or secret key. Walk me through adding the settings to Vercel, then pause for me to deploy.

Names often look like NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY, but follow this app's code rather than guessing. Variables beginning NEXT_PUBLIC_ are included in browser code: never use that prefix for a private credential.

If you add settings after the first deployment, redeploy so the app uses them. If the build fails, open the deployment logs and show Claude the relevant error, with private values removed.

Live authentication

Make login work at the public URL

Supabase needs to know where to send users after confirmation or login. Your local address and live address are different. A successful deployment can still have broken login if those settings point to localhost.

Tell Claude

My Vercel deployment is ready. Inspect this app's auth flow. Add only the exact local and public callback URLs this app needs to Supabase's allowed redirects, preserving existing entries for other course apps. This Supabase project may be shared. Keep its existing Site URL unless we confirm no other app relies on that default and I approve changing it. Make this app pass its own explicit confirmation redirect, such as emailRedirectTo for signup, rather than rely on a shared default. Explain the callback path the code uses. Do not use broad wildcard redirects. Pause for dashboard actions, then give me the live browser checks.

Redirect configuration: Supabase's redirect URL guide. Changing a shared Site URL can affect confirmation or reset links for another course app.

What you should see:

Confirmation and login flows return to your live app, not localhost. Sign-out returns you to the correct signed-out screen.

Final check

Test the app someone else will open

  1. Open the public URL in a fresh private browser window. Confirm the page loads without your development server running.
  2. Create a fresh test account through the live signup form, using an address your configured sender can reach. Open its confirmation email and check that the link returns to the live app. Also test sign-in with an existing confirmed account and sign-out.
  3. Add, edit, complete, and delete tasks. Refresh after each change to check persistence.
  4. Sign in as a second test user. Check that their list is separate. Ask Claude to verify the owner-based policies remain enabled.
  5. Try a phone-width window and bad input. Check for visible errors and no private keys in browser code or the repo.

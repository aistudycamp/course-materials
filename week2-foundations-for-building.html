HOW THIS WORKS

What you are learning

Build with an agent

Claude Code can read the project, edit files, run commands, and check the result. You still make the product decisions and review the work.

Understand the stack

The frontend is the screen. The backend handles rules and requests. The database stores information. Vercel puts the app online.

Work in a loop

Ask for one slice, run the app, look at it in the browser, check the result, then save the working version.

Learn by shipping

The goal is not to memorize commands. The goal is to understand the system well enough to direct Claude and catch problems.

STEP 2

Plan

Before Claude builds, decide what the app is. The plan is where you turn an idea into a small product with a clear user, problem, flow, and first version.

Document the project, plan before code, work in small slices, and review the result.

Read article
Course recording · add before launchSetup and plan

Target 12 to 15 min. Watch this before writing the PRD.

Why plan first?

Claude can write code whenever you ask. That speed makes an unclear idea more expensive, because the app grows before you decide what it should do. A short plan gives Claude something to build and gives you something to review.

What is a PRD?

A PRD is a Product Requirements Document. It is a short description of who the app is for, what problem it solves, what the first version should do, and what can wait. It gives you and Claude the same target before any code is written.

What is Plan mode?

Plan mode is a pause before building. Claude asks questions, challenges unclear decisions, reads the project context, and proposes a build plan. It should not edit the app until you approve the plan.

PRD

The product brief you will review.

Plan mode

The conversation where Claude turns the brief into steps.

Build plan

The ordered implementation steps Claude proposes.

Approval

Your signal that the product and build plan match your intent.

What goes in the PRD?

  • User: who is using the app and what they are trying to do.
  • Problem: what is frustrating, slow, or hard today.
  • Main flow: what happens from opening the app to getting value.
  • Core features: the three things the first version must do.
  • Data: what must still exist after a refresh.
  • Out of scope: what should wait for a later version.

Use Plan mode

In Claude Code, choose Plan mode from the mode selector. Ask Claude to ask you one question at a time, challenge weak decisions, and show you the plan before it edits files.

  • Make a big enough plan to cover the user flow, pages, data, and risks.
  • Ask Claude to grill you until the product is clear.
  • Read the PRD and build plan yourself.
  • Edit anything that is wrong.
  • Tell Claude you approve the plan only when it matches your intent.
Tell Claude: I want to build a small to-do app. Stay in Plan mode. Ask me one question at a time about the user, the problem, the main flow, the visual direction, the data we need to save, and what should wait. Challenge weak or unclear parts of my idea. Save the PRD as PRD.md and the build plan as PLAN.md in this project folder. Do not write code until I approve both files.

PRD template

# Product Requirements Document ## User Who is this for? ## Problem What problem does it solve? ## Main flow What does the user do from opening the app to getting value? ## Core features 1. 2. 3. ## Data What needs to be saved after a refresh? ## Visual direction What should it feel and look like? ## Out of scope What will wait until a later version?
Approve before building:
Read PRD.md and PLAN.md. When they match what you want, say: “I approve this plan. You may begin the foundation.”

STEP 4

Build

Build one slice at a time. Each slice should end with a browser check, not a wall of new code.

Course recording · add before launchBuild the app

Target 20 to 25 min. Watch this while you add the main flow.

Why accounts come later:
Build the task flow first so you can learn how data moves without also debugging account state. Then connect each task to the signed-in user.

Build in this order

1. Core flow

Add, edit, complete, and delete a task. Refresh and confirm the data is still there.

2. Design

Choose the layout, colors, type, and details. Ask Claude for options, then make the call.

3. Accounts

Add sign up, sign in, and sign out after the basic task flow works.

4. Test

Ask Claude to test the flow, inspect errors, and explain anything unclear.

STEP 5

Publish

Publishing moves the app from your computer to a public URL. You will save the code in GitHub, connect the repository to Vercel, add the Supabase values, and test the live app.

Course recording · add before launchTest and publish

Target 15 to 20 min. Watch this before sending the app to a live URL.

Local and live are different:
The local app uses local values. The Vercel app runs online and needs its own Supabase values. A local change reaches the live app only after you commit, push, and let Vercel deploy again.

Git

Saves versions of your code on your computer. A commit is a named snapshot.

GitHub

Stores the repository online and gives Vercel a place to read the code.

Vercel

Builds and serves the app at a public URL.

Environment values

Add NEXT_PUBLIC_SUPABASE_URL and NEXT_PUBLIC_SUPABASE_ANON_KEY in Vercel.

LocalYour computer
CommitSave a version
PushSend to GitHub
VercelBuild online
LivePublic URL

Publish in five steps

  1. Confirm the app works locally.
  2. Ask Claude to review the files for exposed secrets and show you what it will commit.
  3. Approve the file list, then ask Claude to commit and push to GitHub.
  4. Connect the GitHub repository to Vercel and add the two Supabase environment values.
  5. Open the live URL and test sign in, task changes, refresh, and sign out.
Tell Claude: Review this project for exposed secrets. Show me the files you would commit and stop for my approval. After I approve, commit and push the working version to GitHub. Then tell me exactly what I need to add in Vercel before I deploy.

Keep the live URL and a short final test note for your Week 2 submission.
